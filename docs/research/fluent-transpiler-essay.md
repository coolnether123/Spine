# On Rewriting a Method You Did Not Write

There is a particular kind of problem in modding that has no clean solution, only degrees of care. You want to change what a method does, but you did not write the method, you cannot recompile it, and the person who did write it has no idea you exist. Harmony solves most of this elegantly. You can run code before a method, or after it, and for the overwhelming majority of what anyone wants to do, that is enough. You want to know when a pawn finishes a job, you postfix the method that finishes jobs. You want to stop something from happening, you prefix it and return false. Clean, readable, survivable.

And then occasionally you hit the case where it is not enough. The thing you want to change is not the method's beginning or its end. It is a single call sitting in the middle of a loop, forty instructions deep, and the value it returns feeds a comparison you need to influence. You cannot wrap the outside of the method to reach the inside of it. What you actually need is to open the method up and change one instruction in the middle, and that is where transpilers come in, and that is where the ground stops being solid.

A transpiler hands you the method's compiled instruction stream and asks you to hand back a different one. Not source code. The intermediate language the compiler emitted, which is a stack machine, and which does not look much like what the author wrote. There are no variable names worth trusting. Control flow is labels and jumps. A `foreach` has been unrolled into an enumerator dance you have to recognize by shape. And your job is to find your one call in that stream and swap it, without disturbing anything else.

The traditional way to do this is to walk a list of instructions with a for-loop and an index variable, look for an opcode that matches, then splice. It works. It is also about as robust as a house of cards in a stiff breeze, and for a reason worth being precise about: you are pattern-matching against a compiler's output, and the compiler's output is not a contract. The author adds a log line above your call site and every index you computed is wrong. The game updates and a `for` becomes a `while` and your pattern no longer exists. Worse, and this is the part that bites hardest, IL has a stack discipline. Every instruction pushes or pops a known number of values, and at every point where two branches rejoin, both paths must agree on how deep the stack is. Remove one instruction too many and you have not created a bug. You have created a method that the runtime will refuse to execute, and it will refuse at the moment it is first called, which might be an hour into someone's save, in a stack trace that points nowhere near you.

So the question the fluent transpiler system tries to answer is not "how do I edit IL." It is "how do I stop being the person who has to think about all of that, every single time, correctly."

The core idea is to stop describing mechanics and start describing intent. Instead of writing a loop that hunts for a `callvirt` opcode with a particular operand and then performing index arithmetic on a list, you say that you want this call replaced with that one. `ForCall(something).ReplaceWith(somethingElse)`. The finding, the splicing, the bookkeeping — that is the library's problem now, and crucially, it is the library's problem in exactly one place rather than scattered across every mod that ever needed it. There is a small vocabulary of these: replace a call, wrap what a call returns, guard a call so it is skipped under a condition, transform every value a method returns, insert a hook at entry or exit, change a constant, bound-check an argument. Each one is a named intention rather than a recipe for pointer-shuffling, and the set is deliberately small, because the moment a library grows an operation for every situation it has stopped being a library and become a second language nobody asked to learn.

The second idea matters more, and it is about what happens when the pattern is not there. The honest reality of transpiling is that your pattern will eventually not be found — the game updated, or another mod got there first. The traditional failure mode is silence or a crash, and neither is any good. So every operation returns a result rather than assuming success. Found and replaced. Found nothing. Found several and refused to guess which one you meant, because silently patching an arbitrary occurrence is worse than doing nothing. Found something, but it did not look safe. The caller decides what that means. If your mod's whole reason for existing depends on that edit landing, you check the result and fail loudly with a message a human can act on. If it was an optional compatibility path, a clean miss is simply a normal Tuesday and you carry on. That distinction — required versus optional — is one only the mod author can make, so the library refuses to make it for them.

And then there is the stack, because a system that makes IL editing feel easy while still letting you emit an unrunnable method has not made anything easier, it has just moved the cliff further from the fence. So the emitted stream gets analyzed. Not scanned — analyzed, as a graph of basic blocks, tracking how deep the evaluation stack is at every instruction, checking that nothing pops from an empty stack, and checking that when two branches converge they agree about what they are converging with. There is a nice piece of pragmatism in there too: when the analyzer meets a type it does not recognize, because another mod introduced a local it has never seen, it does not panic and it does not guess. It records an unknown of known depth and keeps going. Being wrong loudly about another mod's code would be worse than being usefully vague about it.

The unglamorous work sits underneath all of that, and it is most of the value. Labels have to survive. If an instruction you removed was the target of a jump from somewhere else, that jump has to be moved to whatever now stands in its place, or you have written a leap into empty space. Exception blocks have to survive, since try and finally regions are marked on the instructions themselves and are trivially destroyed by careless splicing. Replacement methods get their signatures checked before anything is mutated, so that passing the wrong argument types is a clear error at patch time instead of a mystery at runtime. And branches into a range you deleted are rejected outright, because that is not a patch, that is a trap.

I want to be straight about the limits, because a tool that oversells its safety is more dangerous than one that admits where the edges are. Methods containing exception handlers currently skip stack validation entirely, which is a meaningful gap given how many interesting methods have a try block in them. In the default profile a critical validation failure is logged rather than thrown, which means it is possible for IL that failed its own check to still reach the runtime. And the case where two independent mods both transpile the same method — genuinely cooperative editing, as opposed to one mod editing alone — has never actually been exercised. There is a result value reserved for reporting exactly that conflict, and nothing in the codebase currently produces it. That is not a claim to make in public until there is a test that proves it, and the test does not exist yet.

What I find quietly satisfying about the whole thing is that almost none of it is about RimWorld. The stack discipline is the CLR's. The instruction stream is what Roslyn emits for any C# assembly. Harmony patches Unity games generally, not one game specifically. The pattern-matching, the label preservation, the exception-region handling, the dataflow analysis — every bit of that is reasoning about .NET intermediate language, and it would work just as well against any Unity game with a Harmony install and a method somebody wants to change from the middle out. The RimWorld-shaped parts are the thin outer layer. What is underneath is a general answer to a general problem, which is the sort of thing that only becomes obvious after you have solved the specific problem carefully enough.

That, in the end, is the argument for building it as a library rather than as a one-off. Every mod that hand-rolls a transpiler is independently rediscovering label preservation and stack balance, usually by shipping the bug first. Doing it once, carefully, in a place with a test harness that patches real methods and asserts on real emitted code, means the next person to need it inherits the caution instead of the crater.
